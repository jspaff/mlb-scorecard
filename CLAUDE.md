# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A self-contained HTML app (`index.html`, ~13,000 lines) implementing a live MLB scorecard widget styled after a traditional paper scorecard, installable as a PWA on mobile home screens. There is no backend, no build step, and no dependencies — all data comes from the public MLB Stats API (plus Baseball Savant for the profile's Defense tab), fetched directly from the browser at runtime.

The whole page is one file: `<style>` (lines ~18-3660), then the markup (`#mlb-root` and its tab panels/overlays), then a single `<script>` IIFE (from ~3812 to the end) containing all the JS. There is no test suite, linter, or package manager config in this repo.

Alongside `index.html` sit the PWA support files: `manifest.json` (name, theme colors, icons), `sw.js` (an app-shell service worker — same-origin GET requests only; it never touches `statsapi.mlb.com`, `baseballsavant.mlb.com` or Google Fonts, so it can't go stale on live data), and `icons/` (generated PNGs, see `sizes` in `manifest.json`). These are separate files by necessity (a manifest must be linked, a service worker must be its own script with its own scope) — the JS/CSS/markup itself stays single-file.

## Running it

There's nothing to install or build. Serve the directory locally (e.g. `python3 -m http.server`) and open `index.html` over `http://`/`https://` — the service worker only registers on http(s), not `file://`, so PWA install/offline behavior needs a server. All calls to `statsapi.mlb.com` and `baseballsavant.mlb.com` are made client-side with plain `fetch()`; there's no proxy or API key involved.

There's no automated way to verify a change — after editing, open the file in a browser and click through the affected tab/overlay to confirm it still works, including a live or in-progress game if the change touches polling or the scorecard grid. Bump `sw.js`'s `CACHE_NAME` on **any change to `index.html`, `manifest.json`, or the icons** (not just edits to `sw.js` itself) — page navigations are network-first (the cache is only the offline fallback), but the manifest and icons are served cache-first and only refreshed in the background for the *next* load, and old caches are only cleared when a new `CACHE_NAME` activates. `install` fetches the shell with `cache: 'reload'` so a new version can't be seeded from the browser's HTTP cache (GitHub Pages sends `max-age=600`); keep that if you touch it. Confirm via DevTools → Application → Service Workers that it updates/activates as expected.

Whenever a Claude Code session edits `index.html` (or `sw.js`/`manifest.json`), attach the updated file(s) to the response (e.g. via a "send file" tool if available) rather than waiting to be asked — the user's workflow is downloading it straight into a local server setup to test.

## Structure

The page is scoped under `#mlb-root` with a set of CSS custom properties (`--paper`, `--ink`, `--gold`, `--brick`, `--frame`) defining the vintage scorecard palette in `:root`. The `PALETTE` JS constant near the top of the script (`const PALETTE = { ink, inkSoft, gold, brick, ball, paper, paperLine, gray, startMuted }`) mirrors those same colors for the handful of SVG strings that can't reference a CSS variable directly — if you change the palette, update both places.

### Tabs

Five tabs — Scorecard, Highlights, Standings, Team, Players — are plain markup (`data-tab-panel` / `data-tab-controls` attributes) driven by a small hand-rolled router near the bottom of the script (the `Tabs` IIFE: `register`/`switchTo`/`init`/`current`). Each tab is registered with an optional `init` (runs once, on first activation) and `onShow` (runs every time the tab becomes active). The active tab is also mirrored into the URL hash, and `Tabs.init('scorecard')` makes Scorecard the default on load (an old `#schedule` or `#roster` link opens Team, which replaced both tabs). Adding a new tab means a `register()` call plus a button + panel in the HTML — there's no routing framework to wire up.

`.tab-header` is sticky, and its real height (it varies by tab, since each tab has its own controls row) is kept in the `--tab-header-h` custom property on `#mlb-root` by `syncSidebarOffsets` — on resize, on any change to the header's own size (a `ResizeObserver`, since web fonts landing or a controls row wrapping changes it without a resize), and on showing the Scorecard and Players tabs. Anything else that sticks below the header (the Scorecard sidebar, the Game Log's column heads and recent-games column) reads that property rather than hard-coding an offset.

### History and the Back button

The app takes part in browser history so the phone's Back button behaves like an app's: it undoes the last drill-in rather than leaving the app. The model, in the block right after the `Tabs` IIFE:

- **Drill-ins push an entry** describing the screen they open — `navPush({ tab, ... })` records the scroll position on the entry being left, then pushes the new one. Opening a player pushes `{ tab: 'players', profile, from, depth }` (`from` is `'list'` or `'other'`, `depth` how many players deep through search), and switching the profile's own tabs replaces that entry with its `profileTab` (`showProfileTab`), so Back to a player lands on the tab he was left on (`showPlayerProfile`'s `tab` option; `renderPlayerProfile` holds a tab that depends on position or season until the person record says whether he has it); opening a game from elsewhere (`jumpToScorecardGame`) pushes `{ tab: 'scorecard', game: { date, pk } }`; opening a popup pushes the current screen's state plus `modals` (see below).
- **Tab-bar switches replace** the current entry (`Tabs.switchTo` does a `replaceState`) rather than pushing, so Back doesn't walk through every tab that was tapped.
- **One `popstate` handler restores** whatever entry Back or Forward lands on: popups first (closing any the entry doesn't list), then the tab (`Tabs.switchTo(id, { history: false })` — the browser has already set the URL), the Players tab's list or profile, the Scorecard's game, and the scroll position.
- Navigating *from another tab* (`jumpToPlayerProfile`, `jumpToScorecardGame`) pushes its entry *before* switching tabs, so the tab being left keeps its own entry and Back returns to it.
- A profile's back link and the Batters/Pitchers toggle go "to the list" through `leaveProfileForList`: `history.go(-depth)` when the profile was opened from the list (so Back and the link agree), otherwise a `replaceState` to the list in place.

When adding a new drill-in, push an entry for it with `navPush` and teach the `popstate` handler to restore it; when adding a new way to *switch* screens within a tab (a date change, a filter), don't push one.

### Players tab

`playersBody` shows either the sortable list or one player's profile — `playersView` (`'list'`/`'profile'`) says which, and `rerenderPlayerProfile` is a no-op unless it's `'profile'`, so a slow profile fetch can't redraw over the list after the user has gone back. The list's filters (`playerListState`) apply client-side over cached rows except season and pool, which pick what's fetched (`playerListCacheKey`). The profile follows the list's season; its data arrives in stages (`showPlayerProfile` → person/career/awards, then `loadProfileSeason` → the season detail and the Overview board, then — only once the Game Log tab is opened — `loadProfileRecent` for the last five games' play-by-play), each stage guarded by `playerProfileRequestId` and each kept in a `lastProfile*` variable that `renderPlayerProfile` reads. The Overview board (`buildProfileBoard` → `renderProfileBoard`) is skill scores: each a percentile (1–100, gold from 90) in one stat, with the stat written small beneath. Hitters get Hitting (Bat wOBA, Power ISO, Contact K%, Eye BB%) and Tools (Speed sprint speed, Range OAA, Glove FRV, Arm; a DH or two-way player gets only Speed, a catcher no Range and his arm from Savant's pop-time board); pitchers get Pitching (Runs ERA, Damage wOBA against with the hitters' weights, Traffic WHIP, Command K%-BB%) and Stuff (Velo, Reach extension, Whiff, Grounders GB%); then Totals (G/HR/SB; GS/IP/K, or a reliever's G/IP/SV). Results stats rank against Savant's bar for its own percentiles, not the batting/ERA titles: hitters with 2.1 PA per team game, pitchers with 1.25 batters faced (`SKILL_POOL_PA_PER_GAME`, `SKILL_POOL_BF_PER_GAME`, out of the season's full player list), pitchers by role -- starters among starters, relievers (`isStartingPitcher` false) among relievers; someone short of his pool is placed among it (`poolPercentile` with `inPool: false`) in softer type, never gold. Statcast tools take Savant's own percentiles where it publishes one (sprint, OAA, arm, fastball velocity, whiff) and are dashed out where Savant doesn't rank him; FRV (among OAA-qualified fielders and Savant's qualified catchers), a catcher's arm, extension and GB% are ranked here (`getSavantSkillData` fetches them all, one CSV each, cached for the session; a DH skips the fielding ones). `loadProfileSeason` starts those Savant CSVs alongside the season stats and draws the board twice: first with the results group and totals (the Stats API's pool, `getProfileBoardPool`), the Statcast group's tiles waiting, then again once Savant is in (`buildProfileBoard` is sync, so the second pass refetches nothing). A hitter's Splits tab has his spray chart, fetched only once that tab opens (`ensureProfileSpray`): one Savant Statcast Search CSV of his season's batted balls (`getPlayerSeasonBattedBalls`, same coordinate space as `hitData`), each hit just its spot, game and at-bat; tapping a dot fills in the popup's pitches, clip and challenges from that game's play-by-play (`hydrateSprayBall` → `battedBallFromPlay`). Savant's data lands overnight, so a game in progress isn't on it yet; seasons before 2008 fall back to sweeping every game's live feed. To keep a profile quick: the Players list warms its season's Savant CSVs while idle (`warmProfileSavant`); a search result's press, and `showPlayerProfile` itself, start the season stats and Savant CSVs before the full person record is in whenever the position is already known (`prefetchProfile`, `profileGroupHint`); the season load starts as soon as the person record is in, with the board's first draw waiting only for the awards row above it (`profileAwardsReady`); a hitter's spray CSV loads in the background once his Overview is done. `once(key, fn)` shares an in-flight request between those callers (person, season stats, league totals, Savant CSVs), and a season in progress keeps its season stats for a minute and its league totals for five. Outfielders, infielders and catchers (`primaryPosition.type`, see `DEFENSE_GROUPS`) also get a Defense tab, loaded only once it's opened (`ensureProfileDefense` → `loadProfileDefense`). Outfielders and infielders get OAA and Fielding Run Value per position plus the group as a whole, both ranked against Savant's OAA-qualified pool for that position (`buildProfileDefense`, `profileDefensePool` picks which); catchers have no OAA, so theirs is FRV and its framing, throwing and blocking parts, ranked against Savant's qualified catchers (`buildCatcherDefense`), with no position toggle. Below the board: outfielders get the catch board from `lastProfileCatches`, whose clips open in the clip popup (`showClipModal`); infielders a double-play ledger (`renderInfieldPlays`, built into scorebook order by `buildDoublePlay`); catchers lamp boards of steals against them by base and their ABS challenges (`renderCatcherPlays`, from `buildCatcherGamePlays`, which tracks who is catching through substitutions, since a stolen base credits no fielder, and reads a challenge recorded on the play rather than its pitch back to the pitch). Infielders and catchers also get MLB's defensive highlight clips of them. All of that comes from `getSeasonFieldingPlays` — a sweep of every game he played there (`/v1/game/{gamePk}/playByPlay` and `/v1/game/{gamePk}/content`, whose highlights tagged `defense` plus his `player_id` are the clips), ~14 MB a season, so it runs only once the Defense tab opens, reports progress straight into its status line, and keeps only the plays it extracts for the session. Catch by catch only exists for the player's latest season. Pitchers (from 2017) get an Arsenal tab, loaded only once it's opened (`ensureProfileArsenal` → `loadProfileArsenal`): the league's pitch-type leaderboards (`getSavantArsenalLeague` — usage, run value per 100, put-away rate; velo and break), which the Overview warms while idle, draw the fastball velo tiles and the movement chart first, then his own season pitch log (`getPitcherPitchLog`, Statcast Search, 1–2 MB, kept as a few fields per pitch) fills in the mix and the two-strike section. `buildProfileArsenal` is sync and every score is a percentile against every pitch of that type thrown 100+ times (`arsenalPools`, per season): fastball velo per fastball type thrown 10%+; each pitch's run value to each batter side (the sum of `delta_pitcher_run_exp`, which reproduces Savant's RV/100 exactly; 50+ pitches to that side to be ranked); and with two strikes (`buildTwoStrikes`), each pitch's share of his two-strike pitches and its put-away rate (matches Savant's `put_away`; 25+ to be ranked), its setup the pitch before his first two-strike pitch of the at-bat (so a foul's repeat isn't one), and the full count (10+ pitches) against the two-strike counts before it, calling out the biggest riser of 8+ points. The movement chart is the catcher's view, true to his hand; Savant's `pitcher_break_x` is a size, its direction the sign of `league_break_x` (negative = arm side). `profileArsenalSide` is the two-strike toggle, defaulting to the side he faced more.

The Highlights tab is `daily` internally (`data-tab="daily"`, `dailyBody`, `dailyPollTimer`, etc.) — it used to be called "Daily", and the user-facing rename wasn't pushed through the internal identifiers; match that if you touch this code. It's one page for a date (no sub-views): `loadDailySummary` → `renderDay`. Its data: one `/v1/schedule` request with `hydrate=linescore,game(content(highlights(highlights)))` (~2 MB a day, so a poll refetches the highlights only every `DAY_MEDIA_TTL_MS`; MLB caps that list at ten clips a game, and `/v1/game/{gamePk}/content` has them all but ignores `fields=` at ~500 KB a game, so it isn't used here), each started game's feed through `fetchGameStats` (home runs, the starters' lines with Game Score, and `keyPlays` — every at-bat with what the diamond needs, its fielders' credits, and its `playId`), and each game's win probability through `getGameWpa` (`/winProbability?fields=atBatIndex,homeTeamWinProbabilityAdded`, ~8 KB a game instead of 1 MB). The page: **Scores** (`renderDayGame` — score boxes, two across a phone, with MLB's recap video on a ▶ and its headline on a wide sheet; a box opens the scorecard), then **Clutch Plays** (the day's biggest WPA swings, at most two of them homers, the biggest non-homer second) and **Web Gems** (MLB's `defense`-tagged clips, `wow` ones first) as swipe rows of video cards, and between them **Out of the Park** (home runs by WPA, Savant Watch links) and **On the Mound** (best starts by Game Score; a start with MLB's outing reel gets a Watch link) as tables, side by side on a wide sheet. `buildClipIndex` → `findClipPlay` ties each MLB clip to its at-bat: a highlight's `id` is either its play's description as a slug or `pitcher-in-play-{run|out}-s-to-batter` (never a strikeout or walk), a hitting clip can also find its batter's scoring plays, a defense clip must match an at-bat its fielder is credited on (`fielderIds`), and a headline's hit type ("RBI double") or inning ("in the 2nd") narrows ties; a defense clip whose id names no at-bat counts only if exactly one credited play fits the inning its headline names. A play with no MLB clip of it (or only a reel that touches it, like "four-hit game") plays Savant's clip of the pitch (`playId`). Every card draws its own still (`renderScorebookStill`: the player's print beside the play's diamond from `diamondSVG`, team and inning above) — MLB's photos aren't shown. No play appears twice on the page.

The Standings tab is team standings only (Division / Wild Card / Playoffs), and all three views share one season picker (`#standingsYearPick`, the same boxed select as the Team tab's, 2000 to the latest season that has started, `getDefaultListSeason`). L10 comes from each team record's `splitRecords` (`type: 'lastTen'`), and the Wild Card cutoff line follows the format of the year (three spots from 2022, two from 2012, one before). `/v1/standings` returns nothing for a date outside the regular season, so `standingsSeasonStatus` (from `/v1/seasons/{year}`) asks for a season in progress as of today and a finished one as of its final day, and the sheet is titled "{year} Final" once the season is over. The Playoffs view (`postseason` internally) is the default from the end of the regular season until next Opening Day: `getPostseasonSeries` (`/v1/schedule/postseason/series`, cached only once the World Series is decided) → `buildPostseasonBracket` → `renderPostseasonBracket`. In the bracket higher seeds sit on the bottom (the `D_1`/`D_3` side, always), and each connector runs into the row the winner takes next, so the LCS card's rows follow bracket position, not home field. The CSS relies on `.pb-team`'s fixed 30px height for that. The bracket is drawn only for the 12-team format (2022 on, series ids `F_1`–`F_4`, `D_1`–`D_4`, `L_1`–`L_2`, `W_1`); earlier seasons are listed by round. A made-up postponed game is listed twice under one `gamePk`, and `buildPostseasonSeries` drops the postponed copy. Tapping a series opens its games in the game-strip popup (`showSeriesGamesModal`, `dataset.mode = 'series'`), and each game opens its scorecard through `jumpToScorecardGame`.

The Team tab (`teamTab` holds its team, season and views; `loadTeamTab` dispatches, guarded by `teamRequestId`) has a team picker, a season picker (2000 to `getDefaultListSeason`, like Standings) and four views. **Overview** (`loadTeamOverview` → `renderTeamOverview`): the team's standings record (`getTeamSeasonRecord`, through `standingsSeasonStatus` like Standings) and, once a season is over, how its October went (`getTeamPostseasonResult`, its deepest series from `getPostseasonSeries`; a champion gets a gold award plate); a W/L/RD/Home/Away/L10 board; the games-over-.500 chart (`renderWinLossSvg`, shared with the Standings popup, drawn twice -- a phone's and a wide sheet's -- with distinct clip ids); and the last five results and next five games as one-line rows that open the scorecard. **Schedule**: the month calendars (`renderScheduleAllMonths`) for that season; a game day opens the game summary popup through `currentScheduleTeam`. **Roster**: for the latest season, sub-tabs Depth Chart / 40-Man / IL (`teamTab.rosterView`; the depth chart stands in for the 26-man). The depth chart (`rosterType=depthChart`, current only, `renderDepthChart`) puts the starters on a drawn field (`DEPTH_FIELD_SVG`, spots in `DEPTH_SPOTS`) with photos, each with any other spots he backs up beside his own position; then the bench as photo cards with the spots each covers (`buildDepthCoverage` -- a starter who also backs up isn't on the bench), and the rotation and bullpen (closer first) as photo cards. Everyone on it gets a photo. List rows carry number, B/T, season age (as of June 30) and position (`fetchTeamRoster` hydrates `person`), and the 40-Man's pitchers split into the rotation in order and the bullpen with the closer first, from the depth chart. An earlier season shows everyone who played (`rosterType=fullSeason`) by name. **Stats**: every player's line for this team (`getTeamPlayerStats` -- `/v1/stats` with `teamId`, so a traded player's line is his line for this team), hitters then pitchers, sortable (`teamStatsSort`, re-rendered from `lastTeamStats` without refetching), with the team's own line (`getTeamSeasonTotals`, `/v1/teams/{id}/stats`) as a footer; names open the full profile, like the Players list. Team-tab names register a `playerStore` entry (`storeTeamPlayer`, never overwriting one a game wrote) so the quick-look popup can open. `fetchTeamSchedule`, `getTeamPlayerStats` and `getTeamSeasonTotals` refetch a season in progress after five minutes (`SCHEDULE_LIVE_TTL_MS`).

The user's team (`myTeam`, picked from the cap at the end of the tab row, `#myTeamPick`) is where the Team tab opens (`populateTeamSelect`) and the Scorecard's default game on a date (`loadSchedule`). It's also marked with a gold wash in Standings and the bracket. A team chosen on the Team tab is browsing and isn't saved; changing your team moves the Team tab.

### Overlays / modals

Pitch detail, roster, player, game summary, team win/loss chart, the Scorecard's game-strip list (also a postseason series' games), and the clip player each have their own overlay `<div>`, a `show*Modal`/`hide*Modal` pair, and are dismissed via close button, backdrop click, the global `Escape` keydown handler at the bottom of the script — or the Back button.

Every overlay must open through `openOverlay(el)` and close through `closeOverlay(el)` (`hidePitchPopup` wraps it), never by toggling the `open` class directly — that's what keeps them in step with history. `openOverlay` pushes an entry listing the popups open over the screen (`state.modals`, mirrored in memory as `modalStack`), so Back closes the top one; `closeOverlay`, used by every other way of closing one, steps history back to match (batched, so `Escape` closing a stack is a single `history.go(-n)`), which leaves no dead entries behind. Each popup's panel is a `role="dialog"` `aria-modal` labelled by its heading; `openOverlay` moves focus to its close button and `closeOverlay` returns it to the opener (`overlayOpeners`, falling back to a matching control in a redrawn sheet), and the global keydown handler keeps Tab inside the top popup. Navigation *out* of a popup (View Full Profile, View Full Scorecard, a Players of the Game name) has to wait for that step back to land before pushing its own entry, or the pending step would pop the new one — wrap it in `whenModalHistorySettled(fn)`, as `jumpToPlayerProfile` and `jumpToScorecardGame` do.

### Live polling

Live-game and daily-summary polling deliberately self-reschedule with `setTimeout` (`scheduleLivePoll` for `pollTimer`, `dailyPollTimer`, `armGameStripPoll`) rather than `setInterval`, so that a fresh call — whether triggered by the user changing dates or by the poll tick itself — can cancel whatever's pending with one `clearTimeout` at the top, and so the next tick is only armed once the last fetch has settled (with a fixed interval, a fetch slower than the interval was superseded by the next tick's request id before it could render, and on a slow connection nothing ever did). Polling only runs while a game's `abstractGameState` is `Live`, every 7s start to start (`LIVE_POLL_MS`, at least 1.5s after a slow fetch lands) for the Scorecard tab and every 15s for the Daily tab's summary.

The Scorecard's live poll is kept cheap and forgiving:
- It fetches with `cache: 'no-cache'`: the feed is sent with `max-age=10` plus `stale-while-revalidate`, so a plain fetch could get the previous poll's copy from the browser's cache. `no-cache` goes no further than MLB's CDN.
- It reads `metaData.timeStamp` off the front of the response text before parsing, and skips the parse and redraw when it matches the feed on screen (`renderedFeedKey`; clear it wherever the grid is replaced).
- A tick that comes due while the Scorecard isn't on screen (another tab, or the app hidden) pauses rather than fetching; the tab's `onShow` and `catchUpAfterResume` pick it back up (`resumeScorecardPolls`). The game strip's poll does the same.
- A failed poll after the game has rendered keeps the grid and the reader's place, dims the board and says when it last updated (`setFeedStale`), and tries again on the usual beat. Only a game that never loaded gets the error plate, with a Try again button (`apiErrorMsg`'s `retry`, handled on `#mlbBody`).
- The redraw puts keyboard focus back on the same control (`focusedControlSelector`).

`clearTimeout`/`clearInterval` alone only stops *future* ticks, though — it can't cancel a call already in flight. Every async load path that can have more than one call outstanding at once (`fetchAndRender`, `loadDailySummary`, `openGameSummaryModal`'s venue/highlights loaders, player search, `showPlayerProfile`) also guards with a bumped `xRequestId` counter, checked right before that call writes to shared state or the DOM, so a slow, now-stale response can never overwrite what a newer call already rendered. Match this when adding a new polling or debounced-fetch path.

### Scorecard rendering (the core feature)

The Scorecard tab turns the live game feed's play-by-play (`allPlays`) into traditional scorecard notation:
- `getPlayCode(play)` derives shorthand like `6-3`, `F8`, `K`, `DP` from the event name and fielder sequence.
- `diamondSVG(...)` draws the small diamond glyph per plate appearance (base-runner lines, out ticks, HR/K shading, special-play labels like `CS`/`PO`).
- `buildTeamRows(...)` / `renderTeamTable(...)` assemble the per-inning batting grid from the boxscore and play list; `renderCellInner` draws one plate appearance's diamond with its runner tags and entering pitcher's plate.

`fetchAndRender` builds `scorecardModel` from each feed (both teams' rows and pitching boxes, the half-innings played, the live half-inning, and for a Final game its highlights) and `renderScorecardSheet` draws it under `scorecardView` (`side`, the team toggle; `half`, the phone's half-inning or `'final'`; `follow`, which keeps both on the live half-inning on every poll until the reader toggles or steps away). The toggle (`setScorecardSide`; during a live game the batting team always means the live half) and stepper (`stepScorecardHalf`, plus "Back to live", `jumpToLiveHalf`) redraw from the model without refetching, and switch views within the tab, so they push no history. Both teams' grids are always drawn (the toggle hides one, `data-side`), and so is the phone's half-inning view (`renderHalfView`), which must render after the grid since the grid's `renderTeamTable` fills `pitchStore` for its cells; CSS shows the grid from 700px up and the half-inning view below it, so turning a phone sideways needs no re-render. The half-inning view lists a half's plate appearances by `order`, the live batter with his pitches (`renderCompactPitchTable`, no count -- the board has it) and the batter on deck; a Final game's last page is the Final summary (`renderGameStory`: play and players of the game from `buildGameHighlights`, shared with the game summary popup, picked by WPA that isn't shown), which is also where a finished game opens, and it's the desktop sidebar's content once a game is Final, and between 700 and 1099px it heads the sheet (`.sc-final-story`). Under each card, `renderPitchingBox` is the other side's staff from the boxscore's `pitchers` (order of entry): the starter's line, then relievers by name; whoever is on the mound gets the gold active rule and a starter who's done says "Final line". Between 700 and 1099px the bottom bar holds the board and the live at-bat as two cards (`#barAtBat`, written by `updateAtBatTrackers` with `renderPitchLocation(..., compact)` -- no plate). The bar's height is kept in `--bar-h` (a `ResizeObserver`) so `#mlbBody` reserves room under it. Under 500px tall (a phone turned sideways) the header and the bar stop sticking and scroll with the page instead, the bar after the card, since together they'd leave the card almost no room. A diamond with pitch detail is a keyboard button (`cellButtonAttrs`: `tabindex`, `role`, an `aria-label` of batter and play; Enter/Space open it in the global keydown handler), and `announceNewPlay` reads each newly completed play into the `#scLive` polite live region -- only within one game, so opening or switching games stays quiet.

A hitter's profile spray chart uses `renderBattedBallFieldSVG`, which draws the field in the API's own hit-coordinate space (`hitData.coordinates`): home plate at `SPRAY_HOME` (125.42, 198.27), `SPRAY_FT_PER_UNIT` ≈ 2.495 ft per unit — a convention checked against MLB's own `totalDistance` on fly balls and home runs. Keep the field and the dots in those same units, so a 400-ft home run lands just past a 400-ft fence.

### Data flow and caching

Functions split into three layers by name: `getX`/`fetchX` (async, hits the API, returns data — the `get`/`fetch` prefix itself carries no distinction, both are used for the same kind of function), `buildX` (sync, transforms raw API data into a structured intermediate like `buildTeamRows`/`buildBullpenList` — not HTML), and `renderX` (sync, returns an HTML string, assigned via `innerHTML` — there's no virtual DOM or DOM-diffing).

Every `getX`/`fetchX` function wraps its `fetch` in its own try/catch and degrades gracefully on failure rather than letting callers deal with a rejected promise — match this when adding a new one. In-memory, module-scoped caches/stores (`gameLogCache`, `standingsCache`, `venueCache`, `playerStore`, `rosterStore`, `pitchStore`, etc.) key off IDs or composite keys (e.g. `` `${personId}-${season}` ``) to avoid refetching when switching tabs or reopening modals within a session; nothing is persisted across page loads. Whether a *failure* gets cached depends on the data, and both cases exist on purpose:
- Static, low-stakes lookups (venue info, player bio/awards) cache `null` on failure — a bad request that stays bad for the rest of the session is a fair trade against hammering a flaky endpoint, and a blank field is a low-stakes degradation.
- Anything that can still change during the session (live game stats, in-progress schedules) does *not* cache a failure — see `fetchGameStats`, which only writes to its cache when `isFinal` and otherwise returns fresh empty results every call, so a transient error doesn't lock in stale/missing data for a game that's still moving.

When adding a new cached fetcher, pick the side of that line matching the data, don't default to "always cache null on error."

MLB Stats API endpoints in use: `/v1/schedule`, `/v1/schedule/postseason/series`, `/v1/standings`, `/v1/seasons/{year}`, `/v1/stats` (league-wide season leaderboards for the Players list, and with `teamId` the Team tab's Stats), `/v1/teams/stats`, `/v1/teams/{id}/stats` (the Team tab's totals row), `/v1/teams/{id}/roster`, `/v1/people` and `/v1/people/{id}` (search, bio, awards), `/v1/people/{id}/stats` (season, yearByYear, gameLog, and statSplits for the player profile), `/v1/venues/{id}`, `/v1/transactions`, `/v1/game/{gamePk}/winProbability` (always with `fields=atBatIndex,homeTeamWinProbabilityAdded`, ~8 KB a game: the Highlights tab's ranking and, through `getGameWpaSigned`, the play and players of the game in the game summary popup and the Scorecard's Final summary), `/v1/game/{gamePk}/playByPlay` (the profile Game Log's last-five hitter cards, the Defense tab's double plays, and a tapped spray-chart hit), `/v1/game/{gamePk}/content` (the Defense tab's highlight clips), and `/v1.1/game/{gamePk}/feed/live` (the live boxscore/play-by-play feed that drives the Scorecard and Highlights tabs). `/v1/schedule` with `hydrate=game(content(highlights(highlights)))` carries each game's recap and top ten clips (mp4s, headlines, tags, player ids) for the Highlights tab.

Baseball Savant (`baseballsavant.mlb.com`, which answers with `Access-Control-Allow-Origin: *`) supplies what the Stats API doesn't: the Defense tab's Outs Above Average, Fielding Run Value (with a catcher's framing, throwing and blocking) and (outfielders only) catch star ratings, and the in-app video clips. Savant's `/leaderboard/abs-challenges` CSV (`challengeType=catcher`) has season ABS totals but names players without ids, so the Defense tab counts challenges from the game feed instead (`reviewDetails` with `reviewType: 'MJ'`). `getSavantOaa` reads the `/leaderboard/outs_above_average` CSV (per position `7`/`8`/`9` or `of`, qualified `min=q` or everyone `min=0`); `getSavantFrv` reads the `/leaderboard/fielding-run-value` CSV per position `2`–`9` (its `position` filter splits a player's runs by position, and a whole group is the sum of its positions; at catcher the default list is the qualified catchers and `minInnings=0` gives everyone, and it carries framing, throwing and blocking runs); the Overview board also reads `/leaderboard/percentile-rankings` (Savant's own percentiles, `type=batter`/`pitcher`), `/leaderboard/custom` (sprint speed; a pitcher's four-seam or sinker velocity, whiff and ground-ball rates), `/leaderboard/outs_above_average` and `/leaderboard/fielding-run-value` across all positions (`pos=`/`position=` empty), `/leaderboard/arm-strength` (`arm_overall` mph), `/leaderboard/poptime` (a catcher's `maxeff_arm_2b_3b_sba`) and `/statcast_search/csv` grouped by pitcher (`group_by=name`, the one place extension comes as a season average, ~270 KB); the Arsenal tab reads `/leaderboard/pitch-arsenal-stats` and `/leaderboard/pitch-movement` (all pitchers, `min=1`) and `/statcast_search/csv` for one pitcher (`pitchers_lookup[]`, every pitch); the profile spray chart reads `/statcast_search/csv` for one batter (`batters_lookup[]`, batted balls only, ~400 KB); `getSavantCatches` reads the `rangeLine: [...]` JSON embedded in the `/savant-player/{id}` page (every catch opportunity with its stars and `play_id`; there's no API for it, it always covers the player's latest season, and it's ~190 KB, so it's fetched once per player, only when the Defense tab opens); `getSavantClip` reads `/sporty-videos?playId=` for a play's mp4, description, date and gamePk, which `showClipModal` plays in `#clipOverlay` (above every other popup) — for the Defense tab's catches and every Watch link (the Scorecard's at-bats, the Highlights tab's home runs and its big moments that MLB has no clip of, the game summary's Play of the Game). Build a new Watch link with `clipWatchAttrs`: it keeps the Savant `href` for open-in-new-tab, and one delegated click handler on `#mlb-root` plays any `a[data-clip-play-id]` in the app on a plain click. A Savant `play_id` is the same id as `playEvents[].playId` in the Stats API's game feed. Leaderboard-wide work (ranks, list columns) belongs on the CSVs, never on per-player pages. The Stats API's own `stats=outsAboveAverage` exists but is wrong (no player is ever below zero) — don't use it.

### HTML building and escaping

There is no `escapeHtml`/sanitization helper anywhere in the file — every `renderX` function interpolates data straight into template strings assigned via `innerHTML`. This is safe only because every value ever interpolated originates from the MLB Stats API or Baseball Savant, never from anything the user types or pastes. The `localStorage` value (below) doesn't break this either, since it's a team ID chosen from a fixed `<select>` and checked against `TEAM_NICKNAMES` on read, not free text. If a future change ever interpolates user-typed input (a search box, a note field, anything) into an `innerHTML` template, it must be escaped explicitly at that point — don't assume the rest of the file's unescaped interpolation makes that safe too.

### Persisted preferences

`localStorage` is used sparingly and only for trivial, session-spanning UI preferences — currently just `mlb-my-team`, the user's team as a team ID string (or `''` for none). It replaced `mlb-schedule-team` and `mlb-roster-tab-team`, which the first load adopts and then removes. Keys are prefixed `mlb-`, and every read/write is wrapped in its own try/catch (private browsing / storage-disabled safety). Keep any new persisted preference this narrow — small values, `mlb-`-prefixed key, try/catch-wrapped — rather than growing an ad hoc storage layer.

## Conventions observed in this codebase

- 2-space indentation, no semicolon-less style — match what's already there.
- Comments are sparse and used specifically to explain non-obvious rationale (a race condition avoided, why a cache is keyed a certain way, why two values must be kept in sync) — not to restate what the code does. Follow that pattern rather than adding narrative comments.
- Everything lives in the one script-level IIFE; there are no ES modules and nothing is attached to `window` except through normal DOM event wiring.
